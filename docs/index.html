Executive summary

Ledgerline is a fictional multi-team invoicing app. Alice Nguyen owns Apex Studio; Bob Okonkwo owns Northwind Labs. The vulnerable schema lets Alice read Bob’s confidential invoices and notes. The fixed schema does not. Tests set auth.uid() the same way Supabase does, then SET ROLE authenticated so Row Level Security actually applies (the database superuser would bypass it).

F-01

Row Level Security is disabled on invoice_notes

Critical

Impact

Postgres leaves RLS off until you turn it on. A table with grants to authenticated or anon and no RLS is readable in full. Alice, a member of Apex Studio, can read Northwind Labs’ internal notes — including “target is evaluating a sale in Q1” and the code name ORCHID.

Repro

-- as Alice, after 0002_vulnerable.sql
SET ROLE authenticated;
SELECT set_config('request.jwt.claim.sub',
  'aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaa1', false);
SELECT invoice_id, body FROM invoice_notes;
-- 4 rows, 2 of them Bob's

Fix (diff)

-- 0003_fixed.sql
+ ALTER TABLE public.invoice_notes ENABLE ROW LEVEL SECURITY;
+ ALTER TABLE public.invoice_notes FORCE ROW LEVEL SECURITY;
+ CREATE POLICY invoice_notes_same_team
+   ON public.invoice_notes FOR ALL TO authenticated
+   USING (team_id = (SELECT p.team_id
+                     FROM public.profiles p
+                     WHERE p.id = auth.uid()))
+   WITH CHECK (team_id = (SELECT p.team_id
+                          FROM public.profiles p
+                          WHERE p.id = auth.uid()));

Test result

BEFORE Alice notes = 4, leaked = 2 AFTER Alice notes = 2, leaked = 0
F-02

USING (true) policy on invoices — RLS is “on” and still leaks

Critical

Impact

RLS was enabled, which looks fine in the dashboard, but the policy allows every row for anon and authenticated. Alice sees INV-B-2001 ($18,900 “Q4 retainer for acquisition target”) and INV-B-2002 ($7,450 “stealth product launch”). “I turned RLS on” is not a fix if the policy is true.

Repro

SET ROLE authenticated;
SELECT set_config('request.jwt.claim.sub',
  'aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaa1', false);
SELECT invoice_number, client_name, memo
FROM invoices;
-- 4 rows, including both Northwind Labs invoices

Fix (diff)

- CREATE POLICY invoices_all_access ON public.invoices
-   FOR ALL TO anon, authenticated
-   USING (true)
-   WITH CHECK (true);
+ DROP POLICY invoices_all_access ON public.invoices;
+ ALTER TABLE public.invoices FORCE ROW LEVEL SECURITY;
+ CREATE POLICY invoices_same_team ON public.invoices
+   FOR ALL TO authenticated
+   USING (team_id = (SELECT p.team_id FROM profiles p
+                     WHERE p.id = auth.uid()))
+   WITH CHECK (team_id = (SELECT p.team_id FROM profiles p
+                          WHERE p.id = auth.uid()));

Test result

BEFORE Alice invoices = 4, leaked = 2 AFTER Alice invoices = 2, leaked = 0 AFTER Bob invoices = 2, leaked = 0
F-03

Service-role key used in client-side code

Critical

Impact

The service_role key is a secret. It maps to a database role with BYPASSRLS. A key shipped in a client bundle, a NEXT_PUBLIC_* variable, or a public repo lets anyone skip every policy — even after F-01 and F-02 are fixed. This demo uses fake keys only; the JWT payload says FAKE DEMO KEY - NOT REAL.

Repro

// src/vulnerable/app/lib/supabase-browser.ts
'use client';
export const supabase = createClient(url, SERVICE_ROLE_KEY);

-- After the SQL fix, as that role:
SET ROLE service_role;
SELECT count(*) FROM invoices;  -- still 4

Fix (diff)

// src/fixed/app/lib/supabase-browser.ts
- export const supabase = createClient(url, SERVICE_ROLE_KEY);
+ export const supabase = createClient(url, ANON_KEY);
// service role stays in supabase-server.ts, never NEXT_PUBLIC_

Test result

service_role after SQL fix: still 4 invoices authenticated Alice after SQL fix: 0 leaked Keys in this repo are fake placeholders
F-04

Missing auth check in the invoices API route

High

Impact

GET /api/invoices?teamId=<victim> never looks at the session. It trusts the query string and reads through the service-role client, so RLS cannot save it. An unauthenticated caller can pull Northwind Labs’ two invoices. This stays broken even if the key is moved server-side, which is why it is a separate finding.

Repro

// src/vulnerable/app/api/invoices/route.ts
export async function GET(req) {
  const teamId = req.nextUrl.searchParams.get('teamId');
  // no getUser(), no membership check
  const { data } = await serviceRole
    .from('invoices').select('*').eq('team_id', teamId);
  return NextResponse.json({ invoices: data });
}

Fix (diff)

+ const { data: { user } } = await userClient.auth.getUser();
+ if (!user) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
+ const { data: profile } = await userClient.from('profiles')
+   .select('team_id').eq('id', user.id).single();
+ if (requestedTeamId && requestedTeamId !== profile.team_id)
+   return NextResponse.json({ error: 'Forbidden' }, { status: 403 });
- .eq('team_id', teamId)          // client-supplied
+ .eq('team_id', profile.team_id) // from the session
// query with the user's JWT + anon key, not service_role

Test result

VULNERABLE API, no session, team B: 2 rows FIXED API, no session: 401 FIXED API, Alice asks team B: 403 FIXED API, Alice own team: 2 rows

Common Supabase RLS holes

A short checklist used in a real audit. The four planted findings above are the ones proven in this sample. The rest are equally common in production apps.

  • 1. RLS never enabledNew tables default to off. A grant to anon or authenticated then exposes every row.
  • 2. USING (true) left from prototypingRLS is “on” in the dashboard, but the policy is a no-op. Same leak as F-02.
  • 3. Service-role key in the clientAny NEXT_PUBLIC_* or browser bundle with that key bypasses every policy.
  • 4. API routes that skip getUser()A server client with the service role and a client-supplied id is a direct object reference.
  • 5. Missing FORCE ROW LEVEL SECURITYTable owners bypass RLS. Fine in hosted Supabase, surprising in local / CI / migrations run as the owner.
  • 6. USING without WITH CHECKReads look correct; INSERT/UPDATE can still write into another team.
  • 7. Client-side filters trusted as security.eq('team_id', myTeam) in the app is not a policy. Change the request, change the data.
  • 8. SECURITY DEFINER functionsA helper that runs as the owner can quietly bypass RLS unless it re-checks auth.uid().
  • 9. Views without security_invokerOn Postgres 15+, a view may run as its owner and skip the caller’s policies.
  • 10. Storage buckets and RealtimeFile objects and subscriptions need their own policies. Table RLS does not cover them automatically.

How the proof is run

No hosted Supabase project is used. auth.uid() is emulated the same way Supabase does, by reading the JWT sub from a session GUC. Tests then SET ROLE authenticated (no BYPASSRLS) or SET ROLE service_role (has BYPASSRLS). That is real SQL RLS, not a mock.

  1. GitHub Actions starts official postgres:16.
  2. tests/run.sh applies 0001_schema.sql, seed.sql, and the vulnerable policies.
  3. It asserts Alice leaks 2 invoices and 2 notes, and that an unauthenticated API call for team B returns 2 rows.
  4. It applies 0003_fixed.sql and asserts 0 leaked rows for Alice and for Bob, a 401 / 403 on the fixed API, and that service_role still sees all 4 invoices (the reason finding 3 exists).

Run it locally with DATABASE_URL=postgres://… bash tests/run.sh. The workflow file is .github/workflows/ci.yml.
